# LOOM 下一步怎么走：给你看的架构方案（讨论版）

> **我们还在讨论，不是现在就开工重构。** 之前我把你转述的“A 一个 Harness，B/C 只有 daemon”当成硬约束，还提前派工写了部分代码，这是理解错误。那份代码先保留作实验，不代表你同意最终架构。这里把你的真正目标和几个选择说清楚。

## 一句话：你要的不是四个 CLI 的统一外壳，而是一个“搬家也不会丢”的 Bot

你喜欢现在的 LOOM 聊天和工作区，想让它更像 **Mikka 的 Bot**：一个有头像、有记忆、知道你有哪些电脑和项目、会拆事和派活、需要你时会问你、做完会拿成果回来给你看的助手。

今天你在 Windows 上用，明天换 Mac 或手机，甚至把 LOOM 的“大脑”搬到 Linux 云服务器，**Bot 还是那个 Bot，聊天、记忆、任务和成果不丢**。电脑 B、C 可以关机、换网、重新连接；只是 Bot 的“手脚”暂时不在。

这件事的核心不是“把 DSH 装到每台电脑”，而是把 **Bot/任务/记忆/授权** 与 **模型运行端**、**设备工具** 分开。

## 你看到的页面，原则上不大改

- **左边**：助手和对话列表。蓝点附近有快捷编辑当前助手。
- **中间**：你和 Bot 聊天；它能说明计划、分工、待你批准的事情、结果和审查。
- **右边**：上方约三分之一展示**当前对话助手的大头像**，眼睛跟鼠标移动；下方才是“工作空间”标题和 **工作 / 资产 / 流程 / 电脑** 四个标签。面板宽度能拖动、记住、双击复位；短屏幕会缩小头像，不遮挡内容。
- **图三**：你给的粉发绿眼猫耳形象做 LOOM 左上品牌 Logo 和浏览器小图标；抠掉原深色底，导出真正透明图。大 Logo 可以动眼睛，favicon 用静态小图；**不覆盖 Hanzi 等助手原来的头像**。

目前右栏头像已经有**雏形**，但图片三品牌资源还没真正进项目，也没有完成你要的全套视觉和卡顿验收。

## 电脑 B 为什么不一定要装 DSH / Pi？

因为“**让 AI 想办法**”和“**让电脑执行鼠标、文件、命令**”是两件事。

例如你在手机对 LOOM 说：“去 B 的工作目录看下项目，再到 C 打开浏览器核对一下。”

**做法一：B/C 只装小助手程序。** 云端 A 的 Pi/DSH 负责理解、规划和调用；B/C 上的小 daemon 像 AgentDock/MindFS 那样接收授权后的文件/终端/浏览器/电脑操作，执行后把证据回传。**这时 B/C 不需要安装模型 CLI**。

**做法二：B/C 也装可选 Runner。** 对大型本地代码仓库，B 上运行 Pi/DSH/Codex 可能更快、减少文件往返，且能使用本地登录环境。A 负责统一目标、权限和结果，B 负责有边界的子任务。DeskFleet/Mikka 的部分设计就是这种路线。

**做法三：两者混用。** 同一台 B 平时只提供文件/屏幕工具，复杂编码任务才启动本地 Runner。**我倾向于把这三种能力都留给 LOOM，而不是现在提前判定哪种“违反架构”。**

**LOOM 不是从零开始。** 它已有远端设备配对、受控工作区工具和“人看/人控”远端电脑的基础；真正没打通的是**云端模型经批准自主调用远端电脑 B**，以及可信公网入口。现在的设备接入有 loopback 限制，助手电脑授权仍偏本机，所以不是装上 DSH 就自动解决。原数据库也允许同一 Mission 在不同 Host 有多条工作区记录，只是当前 API 和清理流程仍按单条处理——应优先补这几处，不重写整套 Core。

## Pi 还是 DSH？

**现在建议不替换 Pi。先把 Pi 作为已经能用的默认内核，DSH 做第二种可选内核，跑同样的测试再决定。**

理由不是 Pi 比 DSH “绝对更好”：你本机 Pi 已经真实跑通过 DeepSeek V4.1 Flash；它有 RPC、Skills、MCP、扩展事件和工具钩子，接入 LOOM 的成本小。DSH 的 Cordis 插件系统更系统化，MOVO 证明它能被封装成企业 Host，值得认真引入；但它在 LOOM 上的封包、权限、跨平台、恢复、四能力生效还没有经过公平验收。

**把模型引擎做成“可更换的发动机”，把 LOOM 的 Bot、记忆、设备和工作记录放在发动机外面。** 以后换 DSH，不应该让你的 Bot 失忆或让所有电脑重新配对。

## 四种能力和记忆怎么管？

想象 LOOM 有一个**能力库**。每项 Skill / MCP / Rule / Hook 都有来源、版本、支持哪个运行端、在哪台设备执行、需要哪些授权。

Claude 配置可以**只读扫描、作为参考源**，但不等于把 Claude Hook 原样复制到 Pi 就会生效，更不能自动执行陌生 Hook。Pi 和 DSH 要各自报告“已加载/真的调用/失败/不支持”。你在 UI 勾选某项，只表示“想让这个 Bot 用它”，不代表它已经拿到了电脑权限。

**记忆是第五层**：Bot 记住你的偏好和工作进度；项目知识可检索；工具结果有来源。你换电脑时记忆留在 LOOM 中心，不必同步到每台电脑的 CLI 目录。

## 权限应该是什么体验？

你可以给某台电脑的某个项目选：

- **Never**：不向你申请额外权限，做不了就拒绝。
- **Ask**：需要额外文件夹、写入、终端或鼠标控制时，明确告诉你“哪个 Bot 要在哪台电脑做什么”，你点批准。
- **Full**：你明确相信这次任务时，在**指定设备/目录/时限**内减少重复询问。

“选择工作目录”只是告诉 Bot 从哪开始，**不是授予全盘权限**。真正的拒绝要在 Core 和电脑 B 本机一起落实；不能只写一句“不要越界”的提示词。

## 我从你给的六个参考里真正想借什么？

**Mikka**：Bot 有自己的身份，右侧大头像、工作状态、派工和“等你处理”的体验。  
**MindFS / AgentDock**：电脑工具独立于 Agent CLI，文件、命令、远程访问可作为服务。  
**DeskFleet**：设备登记、在线状态、PTY/文件/远程桌面、WebRTC 的成熟思路。  
**UFO³ Galaxy**：一个目标拆成依赖任务，按设备能力派发、并行、汇总。  
**AgenTeam**：审批和资源范围分开，工作区路径要真校验。  
**MOVO / DeepSeek Harness**：插件管理、Skill/MCP/规则/Hook、企业权限与知识；**MOVO 的许可对未来多租户和白标有限制，不能直接抄代码**。

Mikka/MindFS 许可已统一为 MIT；设计与公开接口、代码都可复用，整仓嵌入也可以按需评估。

## 建议按什么顺序走？

**第一步，先定方案。** 保留现有 UI 和 Core，明确 Bot、任务、设备、能力、记忆、授权怎么分工；决定“电脑可以只装工具，也可选装 Runner”的产品模型。

**第二步，小规模试验 Pi 与 DSH。** 同一个 DeepSeek V4.1 Flash/max，同样的任务、Skill/MCP/Rule/Hook、授权和恢复测试。没证据不换默认。

**第三步，先让云端 A 真正用 B 的文件/命令，再让 A 在一个目标下同时安排 B 和 C。** 不能拿两个互不相关的测试任务冒充一个 Bot 协调多机。电脑 B/C 可以没有模型。

**第四步，再扩展浏览器、桌面、虚拟屏和更复杂的权限。** Windows 无屏幕、UU/RDP 切换，macOS 屏幕录制权限，必须用真实设备测试。

**第五步，主管亲自打磨 UI。** 把你喜欢的 Mikka 式头像、右栏、Logo、拖动、不卡顿、工作卡做精致，不推翻你现在喜欢的页面。

**第六步，真正把 A 放到 Linux 云端，B/C 连回来；换设备登录仍能使用同一个 Bot。** 单用户稳定后，才做企业组织、共享技能、多人权限。
