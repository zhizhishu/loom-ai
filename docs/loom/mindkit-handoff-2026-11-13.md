## 一、先用人话说架构

LOOM 是**在一台控制主机上运行的多 AI 助手工作台**。你打开网页或桌面 App，跟一个或多个助手聊天，给它们分技能、选工作文件夹、看工作/成果并在需要时审批。页面自己不直接控制模型：它把你的要求交给 Core，Core 再按每个助手选择的运行端和授权找到对应 CLI/执行节点工作。真实任务、任务版本、消息、证据与人工决定都由一个 Core 管理。

~~~text
你（浏览器 / Desktop）
   │ 用户界面 loom-native：助手、群聊、工作、资产、电脑
   ▼
本机 Host 的 Web / Desktop 认证通道
   ▼
Rust Core：唯一的业务事实和调度、版本、授权、审查、接受
   ├── 本机 Runner / CLI adapter：Claude Code / Codex / DSH / Pi
   ├── Node + Workspace：可选的远程 Linux/Windows 执行位置
   ├── SQLite + 受管成果文件：保留本机业务事实
   └── Skills / MCP / Rules / Hooks：按每助手选择和每次运行适配
        └── 各 Runtime 自己连接对应模型（可能经互联网）
~~~

**云端/本机说清楚**：当前用户访问的 Windows 试运行页是该 Windows 主机的 127.0.0.1 本地服务，不是部署在 Bero Linux 的云端 Web。你若通过远程桌面访问这台 Windows，它依然是 Windows 主机本地的服务，不等于运行在你正在使用的另一台终端上。Bero Linux 是本轮测试用机；远端 Node 能做 CLI 工作，但不是所有功能都由 Linux 常驻提供。模型本身可能使用远端云 API，这不意味着 LOOM 数据库已迁到云端。

### 为什么上次没把全部做完

因为上一轮的交付范围实际定为**先让四种能力、助手管理、群聊、工作位置和 UI 真实接到已有 Core**；这与“全套能力真正跨四端和远程机器通用”“接管电脑屏幕”“包一个完整 Pi Agent”“换掉运行 Core”是四个额外的大集成工程。上次避免用假的成功状态掩盖没连上的后端。**这不等于它们不应该做**；用户最终期待的是完整闭环，当前应明确记为未完成产品目标，而不是当成永远不做的决定。

## 五、为什么原页面还没用新 Core

当前只读核对：本机 Windows 试运行的 Host 仍运行原 kit 的 rovai-server.exe；仓库里的新编译 exe 是**另一个 SHA-256**，并非正在执行的文件。页面的 Web 静态资源已被替换到现有 kit，所以你看到**新版 UI + 原 Core**。新 Core 经过隔离独立数据根的真实写入/刷新验收，但并未替换原服务进程。

阻塞不是“新 Core 一定不好”：上次部署守卫要求先知道原试运行进程的完整隔离 HOME / 配置、数据版本与回滚措施；原环境读取遭 Windows 拒绝，清单又未声明完整隔离信息，于是守卫在停止原服务前退出。没有提权、猜环境、强杀或迁移用户数据库。新 Core 仍保留可单独发布的构建，**需要一次有边界的安全部署准备**，不能只说“build 通过所以切”。
